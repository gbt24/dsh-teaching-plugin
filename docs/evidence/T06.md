## 2. 导出接口（Host 接线依据）

```ts
createEnvironmentManager(options: {
  dataDir: string                    // 与 RunnerRegistry 相同的 $DSH_HOME/teaching
  runners: RunnerRegistry            // 只读消费，内置三语言委托
  logger?: (event: string, details?: Record<string, unknown>) => void
  adapters?: ExtendedLanguageSpec[]  // 测试/未来扩展（Ruby/Lua/Deno 默认已含）
  installPlans?: SystemInstallPlanSpec[]
  systemChangeExecutor?: SystemChangeExecutor  // 缺省 = 绝不执行系统级/联网安装
  hostFacts?: Partial<HostFacts>     // 测试注入；缺省读 node:os 实测
  executables?: Readonly<Record<string,string>> // 指定某语言解释器路径
  defaultTimeoutMs?: number; maxOutputBytes?: number
}): EnvironmentManager
```

`EnvironmentManager` 关键方法：`detectNeeds(declared) → Result<EnvironmentNeed[]>`；`prepare(request, {signal, approveSystemChange, onProgress}) → Result<EnvironmentRecord>`；`smoke(environmentId) → Result<ExperimentRun>`；`run(request) → ExperimentRun`（内置委托 registry，扩展语言走独立目录真实进程）；`cancelRun/getRun/activeRuns`；`directory() → EnvironmentDirectory`（含扩展语言行与 gaps）；`cleanup(id)`/`cleanupStale()`/`cancelPreparation(id)`；`assessResources(request)`；`get/getEnvironment/listRecords`（异步，先载入持久化记录）；`dispose()`（中止在途工作，保留已就绪环境与记录）。

异步与错误约定：只有“预期失败”走 `Result`（非法输入）；准备失败/取消/需要确认都返回**记录**（`status` + `failure.cleanup`/`systemChange`），调用方可直接按契约渲染与持久化。`prepare` 对同一语言/方言已有 ready 记录时幂等复用；未批准时重复 prepare 复用待确认记录。

## 5. 失败清理与取消（真实进程 + 真实目录）

证据 harness §4（合成 `/bin/sh` 适配器，让失败/超时发生在真实子进程，不触碰宿主包管理器）：

```text
failure: status=failed code=smoke-failed cleanup=cleaned message=冒烟输出不符合预期：退出码 7，期望 stdout 包含 "42"
failed managed dir exists: false
cancel: status=failed code=cancelled cleanup=cleaned message=准备已取消：冒烟验证期间取消
cancelled managed dir exists: false
persisted records after failure/cancel: t06-evidence-fail:smoke-failed/cleaned, t06-evidence-slow:cancelled/cleaned
```

- 失败/取消都清理未完成目录，`failure.cleanup` 如实写 `not-needed/cleaned/partial/failed`（测试覆盖 `cleaned`、`not-needed`；`partial/failed` 代码路径存在但没有可复现的 fs 故障证据）。
- 失败/取消记录保留在 `state.json`，重启后可读取（见 §7）；重试生成新环境记录，不复用失败目录。
- 已就绪环境不受影响：测试先准备一个可用环境，再让另一个准备失败，之后前者仍 `ready`、冒烟仍 `succeeded`；再次 prepare 同一语言幂等复用原记录。
- `AbortSignal` 与 `cancelPreparation(environmentId)` 两条取消路径均实测（`onProgress` 的 `probe` 事件暴露 id，宿主可在长任务 UI 里取消）。内置三语言委托 RunnerRegistry：其 prepare 无中断接口，取消只停止等待并如实记录“底层准备可能继续”，成功后刷新列表可见（不伪称已取消）。
- 清理只允许 `<dataDir>/environments/managed/**` 内的路径；越界/系统环境返回 `not-needed`/拒绝，不做删除。

## 6. 系统级改动分支：说明、学生确认、**不执行**

证据 harness §5（`go` 真实缺失）：

```text
go need: needs-approval approval=system-change executableByPlugin=false
go commandPreview: brew install go (not executed)
go prepare (no approval): status=needs-approval systemChange.required=true
go isolation note: 未创建任何插件或系统目录；环境未就绪
go prepare (approved, no executor configured): status=needs-approval note=插件未配置系统级安装执行器，不会执行；请按说明自行完成安装后重试。
no system-wide installer was run; only plugin data dir was written
```

- 系统级/联网/插件修复三类改动都生成 `EnvironmentApproval`（description、impact、alternatives、可选 commandPreview、requiresNetwork、`executableByPlugin: false`），并写入 `EnvironmentRecord.systemChange`/`fallback` 供客户端与教学引用。
- 生产默认**没有** `systemChangeExecutor`：即使用户 `approveSystemChange: true`，也只返回/记录 `needs-approval` 与“插件未配置执行器”的说明，不执行命令。
- 仅当 Host/测试注入执行器时，才在**学生批准后**调用一次；测试用注入的假执行器创建一个合成解释器，验证“批准 → 执行一次 → 重新 probe → 独立 prepare → 真实冒烟成功”的完整分支；不批准时执行器调用次数为 0。
- 网络依赖安装即使批准也不执行（v1 只给说明与替代方案）；测试断言执行器零调用。

## 8. 资源受限替代（AC12 / R32）

证据 harness §6：声明“真实大数据集训练大模型”的 envelope（内存 64000 MiB、运行 3600s、数据集 20000 MiB、70 亿参数、需 GPU）对照实测 host facts：

```text
resource status: reduced
reasons: 内存 64000 MiB 超过规划预算 131 MiB | 参数规模估算训练内存约 106812 MiB 超过预算 | 运行 3600s 超过单次交互上限 120s | 需要 GPU，本机状态未探测到可用加速运行时
fallback description: 该实验超出本机资源：……替代方案「小规模过拟合演示：容量与泛化」保留了实验的核心原理，但规模显著缩小（10 个训练点 + 30 个验证点、2 个模型（1 次与 15 次多项式）、闭式最小二乘解）；它可真实运行，但结果不能直接当作完整实验的结论。
full requirements: 内存 64000 MiB（规划预算 131 MiB） | 运行 3600s（单次上限 120s） | 数据集 20000 MiB | 模型参数 7000000000 | GPU（未探测到）
known differences:
  1) 完整规模 vs 替代规模（如上）不同；
  2) 闭式解/极少量样本代替多轮迭代训练：没有 epoch、学习率、优化器状态与真实数据管线；
  3) 参数量/数据量缩小数量级，训练/验证差距只用于观察方向，不代表真实模型绝对精度；
  4) 合成数据与真实课程数据的噪声、类别分布不同，指标不可直接对比。
caveats: 只用于教学演示原理，不能声称复现完整实验数值/性能 | 合成数据/简化模型 | 完整规模需更强硬件或外部资源，第一版不管理远端计算
reduced run: status=succeeded verification=objective checks=pass,pass,pass
reduced run stdout:
underfit(degree=1): train=0.0431 holdout=0.0537
overfit(degree=15): train=0.0000 holdout=0.2765
REDUCED-SCALE: 10 训练点 + 30 验证点、纯 Python 闭式解；观察容量与泛化的差异
```

- 替代方案不是文案：`reducedExperiment` 带 code/checks/timeout，由真实 Python/JS 运行并通过 objective checks（训练/数值/模拟三类各有 Python 版；JS 声明用 JS 版）。
- 资源判定使用实测 `node:os` 事实（total/free/cpus），预算取 `min(free×50%, total×25%)` 且不低于 128 MiB；GPU 状态未探测 → `unknown`，不假设可用。
- `simulation` 类返回 `status: simulated`（确定性平均场 SIR 示例真实运行）；无法自动生成替代的 `other` 类返回 `status: 'none'`、无 `reducedExperiment`，并在 description/caveats 明确“未自动生成可运行替代，不得报告为已运行”。
